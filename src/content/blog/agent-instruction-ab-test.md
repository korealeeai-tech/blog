코딩 에이전트를 오래 쓰다 보면 지시문 파일이 계속 길어진다. 실수가 한 번 나면 그 실수를 막는 문장을 하나 더 넣는다. "반드시 검증한다", "확정 전에는 파일을 고치지 않는다", "보고는 네 줄로" 같은 문장들이다. 넣을 때는 다 이유가 있었다. 문제는 그 문장이 지금도 무언가를 하고 있는지 아무도 확인하지 않는다는 점이다.

Anthropic의 모델별 프롬프트 가이드에는 이 문제를 정면으로 다루는 문장이 있다.

Review and consider removing older instructions if default performance is better."

마지막 조건절이 핵심이다. "기본 성능이 더 나으면" 지우라고 했지만, 기본 성능이 더 나은지는 문서가 대신 알려주지 않는다. 직접 재야 한다. 그래서 내 작업 환경에서 실제로 쓰던 지시 네 가지를 골랐다. 지시문 파일, 작업 기억 파일, 세션 시작 때 주입되던 스킬 문구에 흩어져 있던 것들이다. 각각을 한 절로 옮긴 뒤, 그 한 절만 다른 두 CLAUDE.md로 같은 과제를 실행해 봤다.

**규칙 한 절을 넣었을 때와 뺐을 때, 에이전트가 실제로 하는 일이 달라지는가?**

[규칙을 적어도 왜 지켜지지 않는지](/blog/blog/ai-rules-need-validation-gates/)를 다룬 글은 지시문이 강제가 아니라 문맥이라는 쪽에 무게를 뒀고, [지시문을 세 계층으로 나누는 기준](/blog/blog/ai-agent-instruction-diet/)은 배치 원칙을 합성 예시로 분류하면서 비교 실험은 하지 않았다고 밝혔다. 이 글은 그 빈칸을 실행 결과로 채운다. 결론부터 말하면 이번 실험에서 행동을 크게 바꾼 규칙은 "더 하라"는 규칙이 아니라 "먼저 멈추라"는 규칙이었다.

## 실험 설계: 같은 코드, 같은 과제, 규칙 한 절만 다르게

실험 대상은 파일 네 개짜리 합성 Python 프로젝트다. 평균과 변화율을 계산하는 `calc.py`, 그것을 출력하는 `cli.py`, 지저분한 출력을 내는 `report.py`, 그리고 테스트 파일이다. 테스트 파일에는 `percent_change(0, 10)`이 `None`을 돌려줘야 한다는 테스트가 처음부터 실패하는 상태로 들어 있다. 원래는 A 과제가 고쳐야 할 기준으로 넣은 것인데, B·C·D 과제에서는 과제와 무관한 기존 실패가 됐다. 덕분에 에이전트가 범위 밖 실패를 어떻게 다루는지도 함께 볼 수 있었다. 프로젝트 안에는 코딩 표준과 보고 규격을 적은 짧은 문서 두 개도 `docs/protocols/`에 넣었다.

기본 CLAUDE.md는 두 줄뿐이다. 한글로 답하고, 표준 라이브러리만 쓰고, 테스트는 `python3 -m unittest`로 돌린다는 내용이다. 규칙이 있는 조건에서는 이 파일 끝에 규칙 한 절을 붙였다. 네 규칙과 각 규칙을 시험한 과제는 다음과 같다.

| 규칙 | 규칙 문장의 요지 | 과제 |
|---|---|---|
| A 검증 재촉 | 완료 전에 반드시 검증하고, 결과를 confirmed·refuted·uncertain·gaps로 나누고, 마지막에 한 번 더 확인한다 | old가 0이면 `None`을 돌려주도록 `percent_change`를 고친다 (명확한 버그 수정) |
| B 확정 전 수정 금지 | 비단순 작업은 의도를 추론하고, 모호하면 확인 질문으로 확정하기 전까지 파일을 고치지 않는다 | "report.py 출력 좀 정리해줘" (일부러 모호하게) |
| C 보고 형식 강제 | 네 줄 보고를 하고, 검증 줄에 규칙 문서를 읽은 뒤 파일명과 함께 인용한다 | `cli.py`에 `--verbose` 옵션 추가 |
| D 1% 절차 강제 | 1%라도 해당하는 절차가 있으면 반드시 따르고, 기능 추가 전에는 질문과 설계안 선택을 먼저 거친다 | `cli.py`에 `--json` 옵션 추가 (명확한 소형 기능) |

D는 한 스킬 묶음이 세션 시작 때 주입하던 강제 문구의 어조를 본떠 썼다. 그 스킬 묶음 자체를 시험한 것이 아니라, 그런 어조의 문장 한 절을 시험했다는 점을 분명히 해 둔다.

실행 조건은 2026-09-03 기준으로 Claude Code CLI 2.1.259, 모델 Claude Fable 5.1(`claude-fable-5-1`), effort `high`, headless 실행(`claude -p`)이다. 매 실행마다 fixture를 새 폴더에 복사하고 git 기준 커밋을 만든 뒤 `--setting-sources project`로 실행했다. 실행 로그의 시작 이벤트에서 플러그인과 MCP 서버가 빈 목록인 것을 확인했고, 사용자 전역 CLAUDE.md는 없는 환경이었다. 규칙 4개 × 있음/없음 × 2회로 16회를 돌렸고, CLI가 보고한 비용 합계는 약 $5.82였다.

본 실행 전에 정해 둔 비교 항목은 턴 수, 도구 호출 수, 에이전트가 직접 테스트를 돌렸는지, 변경 파일, 편집 없이 질문으로 끝났는지, 출력 토큰과 시간이다. 권한 거부가 하나라도 있으면 무효로 본다는 기준은 아래의 첫 시도가 실패한 뒤, 두 번째 실행 전에 정했다. 기존 실패 테스트를 보고했는지와 작업 폴더 독립 판정은 결과를 본 뒤에 추가한 항목이다.

## 첫 16번은 하네스를 잰 것이었다

처음 돌린 16회는 결과로 쓰지 않았다. 16회 중 14회에서 권한 거부가 났고, 그런 실행 대부분은 고치겠다는 말만 남기고 파일을 바꾸지 못했다. stream-json 로그의 `permission_denials`를 세어 보니 원인이 두 가지로 갈렸다.

첫째, 실험 폴더를 `~/.claude/` 아래에 만들었다. 그 경로의 파일은 전부 민감 파일로 판정돼 Edit 14건과 Write 9건, 합계 23건이 거부됐다. 둘째, 셸 허용 목록을 `Bash(python3 *)`처럼 접두어 패턴으로 좁혀 뒀다. 셸 명령 거부 14건은 원인이 여러 가지였다. 승인이 필요하다는 거부가 6건(그중 3건은 `cd ... && ...` 같은 복합 명령의 일부), `find -exec`는 접두어 규칙으로 자동 허용할 수 없다는 거부가 4건, 명령 해석 단계에서 걸린 것이 2건, 허용된 작업 폴더 밖으로 이동하려다 막힌 것과 민감 경로가 1건씩이었다. headless 모드에서는 이런 명령이 승인을 기다리지 않고 바로 거부된다.

거부가 없던 2회는 B와 D 규칙이 있는 조건이었고, 둘 다 두 번째 실행과 마찬가지로 질문으로 끝났다. 그래도 나머지와 권한 조건이 달라서 첫 시도 전체를 버렸다. 이 실패를 결과로 읽었다면 "규칙과 상관없이 에이전트가 소극적이다"라는 엉뚱한 결론이 나왔을 것이다.

그래서 실험 폴더를 홈 아래 일반 작업 폴더로 옮기고 셸 허용을 넓혔다. 파일럿 1회로 거부가 없는 것을 확인하면서, 로그 파일이 변경 파일 목록에 섞이던 문제도 고쳤다. 그 뒤 다시 돌린 16회는 권한 거부 0건, 모두 정상 종료였다. 아래 결과는 전부 이 두 번째 실행이다. 파일럿 1회($0.373)는 비용 합계에 넣지 않았다.

## 결과: 바뀐 것과 바뀌지 않은 것

에이전트 로그에서 센 값과, 실행이 끝난 작업 폴더를 따로 판정한 값을 함께 적었다. 독립 판정은 과제를 실제로 만족하는지(예: `--json` 출력이 JSON으로 파싱되는지, 기본 출력이 그대로인지)를 에이전트의 자기 보고와 무관하게 다시 실행해 확인한 것이다.

| 규칙 | 규칙 없음 (2회) | 규칙 있음 (2회) | 달라진 것 |
|---|---|---|---|
| A 검증 재촉 | 수정 2/2, 테스트 실행 2/2, 과제 충족 2/2 | 수정 2/2, 테스트 실행 2/2, 과제 충족 2/2 | 4분류 보고, 수정 뒤 grep 0/2 → 2/2 |
| B 확정 전 수정 금지 | 수정 2/2, 테스트 실행 2/2 | 질문으로 끝 2/2, 수정 0 | 구현 대신 질문 |
| C 보고 형식 강제 | 네 줄 보고 2/2, 과제 충족 2/2 | 네 줄 보고 2/2, 과제 충족 2/2 | 규칙 문서 파일명 인용 0/2 → 2/2 |
| D 1% 절차 강제 | 수정 2/2, 과제 충족 2/2 | 설계안 선택 질문 2/2, 수정 0 | 구현 대신 질문 |

### A: 결과물은 같았고, 재확인 절차와 보고가 달라졌다

검증을 재촉하는 규칙이 있든 없든 에이전트는 네 번 모두 테스트를 돌렸고, 독립 판정에서도 네 번 모두 `None` 반환과 기존 정상 계산을 함께 지켰다. 결과물 기준으로는 차이가 없었다.

차이는 절차와 보고에서 났다. 마지막 수정 뒤에 grep으로 코드를 다시 훑은 실행은 규칙 있는 쪽 2/2, 없는 쪽 0/2였고, 수정한 파일을 다시 읽은 실행은 규칙 있는 쪽 한 번뿐이었다. 도구 호출 수는 12·7 대 5·7이었다. 보고는 규칙 있는 쪽이 confirmed·refuted·uncertain·gaps 네 칸을 그대로 썼고, 없는 쪽은 산문으로 짧게 썼다. 출력 토큰은 규칙 있음 2,495·1,758, 없음 866·1,905로 방향이 한쪽으로 모이지 않았다.

이 차이를 어떻게 읽을지는 서로 반대 방향인 두 장면이 함께 보여 준다. 첫 장면은 독립 판정에 넣은 관찰 항목에서 나왔다. 과제 문장에는 없는 항목이다. `percent_change`가 이제 `None`을 돌려주니, 그 값을 소수점 형식으로 찍는 `cli.py`는 첫 숫자가 0이면 `TypeError`로 죽는다. 이 호출부까지 고친 실행은 양쪽 모두 1/2이었다. 차이는 고치지 않은 두 실행의 보고에서 났다. 규칙이 있던 실행은 gaps 칸에 이렇게 남겼다(발췌, 코드 표시는 뺐다).

```text
gaps (요청 범위 밖이라 손대지 않음)
- cli.py:11-13은 percent_change 결과를 {change:.2f}로 포맷합니다.
  첫 숫자가 0이면 이제 ZeroDivisionError 대신 TypeError가 납니다.
```

규칙이 없던 실행은 테스트 세 개가 통과했다는 말로 끝났고 호출부 이야기는 없었다.

두 번째 장면은 같은 실행의 confirmed 칸에 있다. 그 칸에는 "변경 파일 재읽기와 grep으로 잔여 ZeroDivisionError 관련 문구가 없음을 확인했다"고 적혀 있다. 그런데 로그에는 수정 뒤 파일을 다시 읽은 호출이 없고, grep은 수정한 `calc.py`가 아니라 `report.py`를 대상으로 했다. 규칙이 요구한 확인 항목을, 실제로 하지 않은 부분까지 확인했다고 보고 칸에 채운 것이다.

두 장면 모두 한 번씩이라 일반화할 수는 없다. 이번 관찰로 말할 수 있는 것은 여기까지다. A 규칙은 결과물을 바꾸지 않았고 보고를 더 구조화했으며, 그 구조 안에는 쓸모 있는 경고와 근거 없는 확인이 함께 들어갔다.

### C: 보고 형식은 규칙보다 문서가 먼저 만들었다

C 규칙이 요구한 네 줄 보고는 규칙이 없어도 네 번 모두 나왔다. 로그를 보면 규칙이 없던 두 실행도 `find docs -type f -exec cat {} \;` 같은 명령으로 `docs/protocols/`를 스스로 읽었다. 그 폴더의 보고 규격 문서에 네 줄 형식이 이미 적혀 있었으니, 규칙 문장이 없어도 같은 형식이 나온 셈이다. 규칙이 없던 8회 전체로 넓혀 보면 관계가 더 분명하다. 문서 폴더를 연 5회는 모두 네 줄 보고를 썼고, 열지 않은 3회는 한 번도 쓰지 않았다. 규칙이 추가로 만든 것은 검증 줄에 `coding-standards.md`라는 파일명을 적는 습관뿐이었다.

이 결과는 깔끔하게 분리된 측정이 아니다. fixture 문서가 규칙 내용을 이미 담고 있어서, 순수한 규칙 효과와 문서 효과를 떼어 낼 수 없다. 대신 실제 저장소와 조건이 비슷하다. 대부분의 저장소에도 이미 규격 문서가 있고, 에이전트는 그 문서를 찾아 읽는다.

### B: 질문으로 멈췄고, 질문 속 설계안은 규칙 없는 결과물과 같았다

B 규칙이 있는 두 실행은 `report.py`를 읽고 직접 실행해 본 뒤, 어떻게 바꿀지 설계안을 보여 주고 질문 두 개를 남긴 채 끝났다. 파일은 하나도 바뀌지 않았고 테스트도 돌리지 않았다. 한 실행은 마지막에 이렇게 썼다.

```text
답을 주시면 바로 수정하고 python3 report.py와 python3 -m unittest로 검증하겠습니다.
별다른 지시가 없으면 1번은 삭제, 2번은 없음으로 보고 진행하겠습니다.
```

headless 실행에서는 그 "별다른 지시"가 오지 않는다. 진행하겠다는 문장이 마지막 출력이 되고 작업은 거기서 끝난다.

규칙이 없는 두 실행은 디버그 줄을 걷어내고 항목·처리·성공·실패를 정렬한 표로 바꿨다. 둘 다 테스트를 돌렸고, 처음부터 실패하던 테스트는 이번 수정과 무관하다고 보고했고, `git stash`로 수정 전 기준선과 비교해 그 실패가 원래 있던 것임을 확인했다. 그리고 이 두 실행이 만든 표는, 규칙 있는 실행이 질문하면서 "이렇게 바꾸려고 한다"고 제안한 표와 사실상 같았다. 질문에 답이 왔다면 무엇이 달라졌을지는 이 실험으로 알 수 없다. 다만 질문 속 설계안과 규칙 없이 만든 결과물이 같았으므로, 이번 과제에서 질문이 결과를 바꿨을 가능성은 낮다고 본다.

그렇다고 B가 잘못 작동했다고 볼 수는 없다. 공식 가이드는 정확히 이런 동작을 원할 때 쓰라고 비슷한 프롬프트를 예시로 준다.

B 규칙은 문서가 의도한 방향으로 작동했다. 남는 질문은 그 동작이 언제 이득이냐는 것이다. 이 과제는 일부러 모호하게 냈는데, 에이전트가 추론한 설계는 규칙 없는 실행이 만든 결과물과 같았다. 추측이 빗나갈 과제였다면 같은 질문이 잘못된 수정 한 번을 막았을 수도 있다. 이 실험은 그 경우를 시험하지 않았다. 어떤 모호성은 질문해야 하고 어떤 모호성은 조사로 풀 수 있는지는 [짧은 요청으로 작업 범위를 정하기 어려운 이유](/blog/blog/why-ai-keeps-guessing-user-intent/)에서 원칙으로 다뤘다. 이번 결과는 그 구분이 지시문 한 줄만으로는 잘 지켜지지 않을 수 있다는 관찰이다.

### D: 명확한 작은 기능도 설계 회의가 됐다

D가 가장 분명했다. `--json` 옵션 추가는 모호한 요청이 아니다. 규칙이 없는 두 실행은 옵션을 붙이고, 기본 출력을 그대로 두고, 그중 하나는 테스트 파일까지 새로 만들었다. 독립 판정에서도 두 번 모두 `--json` 출력이 JSON으로 파싱됐고 기본 출력은 바뀌지 않았다.

규칙이 있는 두 실행은 코드를 다 읽고, 기존 실패 테스트까지 짚어 낸 뒤, JSON 키를 영문으로 할지·입력값을 포함할지·한글 키로 할지 세 안을 내밀고 끝났다. 한 실행은 "어느 쪽으로 할지 골라 주시면 다음 질문(…)으로 넘어가겠습니다"라고 썼다. 질문이 한 번으로 끝나지 않을 예정이었다는 뜻이다. 두 실행 모두 추천안까지 스스로 골라 놓았다. 추천안은 영문 키에 원래 정밀도를 그대로 둔 구조였는데, 규칙 없이 만든 두 결과물이 실제로 그 구조였다. 둘 다 `cli.py --json 1 2 3`에 `{"average": 2.0, "percent_change": 200.0}`을 출력했다.

공식 가이드에는 강한 어조의 지시에 관한 경고도 있다.

이 문장은 도구나 스킬을 덜 쓰던 시절에 넣은 "CRITICAL", "MUST" 같은 표현이 새 모델에서는 과하게 발동한다는 맥락이다. D 규칙의 "선택이 아니다. 협상 불가다" 같은 표현과 결이 같지만, 문서가 Fable 5.1에 대해 같은 말을 했다는 뜻은 아니다. 내가 확인한 것은 이 모델이 그 문장을 두 번 모두 충실히 따랐다는 관찰까지다.

## 규칙 없이 이미 나오던 행동

비교를 위해 규칙이 없던 8회만 따로 보면, 이 모델의 기본 행동이 꽤 단단했다는 점이 드러난다.

- 8회 모두 스스로 `python3 -m unittest`를 돌렸다.
- 처음부터 실패하던 테스트가 과제와 무관한 B·C·D의 6회 모두, 그 실패를 범위 밖 문제로 보고하고 손대지 않았다. 테스트 파일을 고쳐서 통과시킨 실행은 16회 중 한 번도 없었다.
- 3회는 `git stash`로 수정 전 상태와 비교해 그 실패가 원래 있던 것임을 확인했다.
- `docs/protocols/` 폴더를 직접 연 실행은 8회 중 5회였다(C 2/2, D 2/2, B 1/2, A 0/2).

마지막 숫자는 한 번 고쳤다. 실험 당일 기록에는 "8/8"로 적혀 있었는데, 이번에 도구 호출을 다시 세어 보니 5/8이었다. 처음 다시 셀 때는 경로에 `protocols`가 들어간 호출만 세서 더 적게 나왔다. 에이전트가 `find docs ...`처럼 폴더 이름만 쓰고 읽은 경우를 놓쳤기 때문이다. 독립 판정기도 처음에는 `--verbose` 출력을 표준 출력만 세다가, 상세 줄을 표준 에러로 보낸 두 실행을 실패로 잘못 판정했다. 둘 다 결과를 보고 고친 측정이라 숨기지 않고 적는다. 에이전트 결과를 의심하기 전에 내 계측부터 의심해야 했던 사례다.

A와 C가 요구한 행동 가운데 테스트 실행과 규격 문서 참조는 이 모델이 규칙 없이도 대부분 하고 있었다.

## 왜 "멈추라"는 규칙이 가장 세게 먹혔을까

여기부터는 관찰이 아니라 해석이다. 내 설명은 이렇다. "더 하라"는 규칙은 모델이 이미 하는 일을 다시 요구하기 때문에 바꿀 행동이 별로 없다. 남는 차이는 보고에 그 일을 어떻게 적느냐뿐이다. 반면 "먼저 확인하라"나 "설계 질문 없이 코드를 쓰지 마라"는 규칙은 행동 앞에 조건을 건다. 그 조건을 가장 싸게 만족하는 방법은 질문하고 멈추는 것이다. 지시를 잘 따르는 모델일수록 그 경로를 충실히 탄다.

이 설명과 맞지 않을 수 있는 경쟁 설명도 있다. 첫째, 과제와 규칙이 짝지어져 있다. B 규칙은 모호한 과제에서만, D 규칙은 명확한 소형 과제에서만 시험했다. B가 질문으로 끝난 이유가 규칙 때문인지, 모호한 과제 때문인지 이 실험만으로는 완전히 떼어 낼 수 없다. 다만 같은 모호한 과제에서 규칙이 없을 때는 두 번 다 바로 구현했으니, 적어도 규칙이 방향을 바꾼 것은 맞다. 둘째, headless라는 조건이 결과를 키웠다. 사람이 대화창에서 바로 답할 수 있는 환경이라면 질문은 몇 초짜리 왕복일 수 있다. 이 실험에서는 질문이 곧 작업 종료였다.

## 그래서 어떻게 할 수 있나

규칙 하나를 앞에 두고 고를 수 있는 길은 대략 네 가지다.

**그대로 둔다.** 되돌리기 어려운 작업이나 해석이 갈리는 요청에서는 확인 질문이 실제로 비싼 실수를 막는다. 사람이 곁에서 답해 줄 수 있는 대화형 작업이라면 왕복 비용도 작다. 대신 명확한 작업까지 멈추는 비용을 감수해야 한다.

**지운다.** 기본 행동이 이미 그 일을 한다면 가장 단순하다. A와 C가 그런 후보였다. 하지만 A의 gaps 장면처럼 형식이 남은 위험을 드러내는 경우가 있어서, 지울 때 무엇을 잃는지 먼저 봐야 한다. 같은 형식이 하지 않은 확인을 했다고 적게 만든 장면도 있었으니, 남긴다면 보고 칸의 주장을 로그와 대조하는 장치가 함께 있어야 한다. 모델이 바뀌면 기본 행동도 바뀐다는 점도 감안해야 한다.

**조건을 좁혀 다시 쓴다.** 공식 가이드의 보수적 실행 예시도 "의도가 모호할 때"라는 조건을 달고 있다. B 규칙에도 "모호성이 있으면"이라는 조건이 있었고, 일부러 모호하게 낸 과제였으니 발동한 것 자체는 맞다. 다만 에이전트가 스스로 추론한 설계가 규칙 없는 실행이 실제로 만든 결과물과 같았는데도 멈췄다. "모호하다"의 문턱이 어디인지는 문장만으로 정해지지 않는다는 뜻이다. D는 "1%라도"라는 표현 때문에 사실상 조건이 없었다. 조건을 적는 것과 그 조건이 실제로 어떻게 해석되는지는 다른 문제라서, 고쳐 쓴 뒤 같은 과제로 다시 돌려 봐야 한다.

**실행 시점의 장치로 옮긴다.** 정말 막아야 하는 것이 삭제나 배포처럼 되돌리기 어려운 동작이라면, 문장 규칙보다 권한 설정이나 hook으로 그 동작만 막는 편이 정확하다. 모든 수정 앞에서 멈추게 하는 문장 대신, 위험한 명령에서만 멈추게 하는 장치를 두는 방식이다.

이 실험 뒤 내 지시문에서 실제로 바꾼 것은 한 줄이다. 요청이 명확하고 설계 선택지가 실제로 갈리지 않는 작은 변경은 질문 없이 바로 구현하고, 이 줄이 "1%라도" 문구보다 우선한다고 적었다. 명확한 소형 과제를 결과물 없이 질문으로 멈추게 한 D의 효과만 꺾으려는 선택이었다. A와 C는 결과물을 해치지 않았으므로 남겼고, B는 완화안을 만들어 두었지만 그때는 적용하지 않았다. 새로 넣은 그 한 줄이 실제로 질문을 줄였는지는 아직 같은 방식으로 재지 않았다.

```bash
git clone --depth 1 --filter=blob:none --sparse https://github.com/korealeeai-tech/blog.git
cd blog
git sparse-checkout set public/blog-examples/instruction-ab
cd public/blog-examples/instruction-ab
```

그 폴더에서 다음처럼 실행한다. Claude Code가 로그인된 상태여야 하고, `git`과 Python 3가 필요하다. 이 글과 같은 모델을 쓰려면 별칭 대신 전체 모델 ID를 준다.

```bash
REPS=2 PARALLEL=4 MODEL=claude-fable-5-1 EFFORT=high bash run_all.sh
```

실행 결과는 예제 폴더 밖의 작업 폴더(기본값 `${TMPDIR:-/tmp}/instruction-ab-work`, `WORK`로 바꿀 수 있다)에 생긴다. 끝나면 그 아래 `metrics.json`에 실행 로그 요약이, `grades.json`에 독립 판정이 남는다. 실행 로그에는 내 환경의 절대경로가 들어가므로, 공개 저장소 안에 작업 폴더를 두지 않도록 기본값을 바깥으로 잡았다. 내 실행에서는 한 회에 17~70초가 걸렸고 16회 비용은 CLI 보고 기준 약 $5.82였다. 다른 모델이나 effort로 돌리면 이 숫자는 달라진다.

결과를 읽기 전에 먼저 `metrics.json`의 `valid`를 본다. `false`라면 모델이 아니라 하네스를 잰 것이다. 이때 확인할 곳은 네 군데다. 작업 폴더가 `~/.claude/` 아래에 있지 않은지, 셸 허용을 접두어 패턴으로 좁히지 않았는지, 상위 디렉터리에 다른 CLAUDE.md가 있어 섞이지 않았는지, run마다 남는 `stderr.txt`에 명령을 찾지 못했다는 오류가 없는지다. 사용자 전역 `~/.claude/CLAUDE.md`가 있다면 그 내용이 두 조건 모두에 섞일 수 있다. `--setting-sources project`가 이 파일까지 빼는지는 확인하지 않았으니, 실험하는 동안 잠시 옮겨 두거나 결과를 해석할 때 감안한다. 그리고 이 하네스는 에이전트에게 셸 전체를 허용한다. 버려도 되는 폴더나 컨테이너에서만 돌려야 한다.

내 지시문의 규칙을 시험하려면 `rules/` 아래 파일을 내 규칙으로 바꾸고, `tasks.txt`에 그 규칙이 실제로 개입할 만한 과제를 하나씩 적으면 된다. 규칙이 멈추게 만드는 쪽이라면 일부러 명확한 과제를 하나 넣어 보는 것을 권한다. 이번 실험에서 가장 많이 배운 것이 그 조합이었다.

공개 스크립트는 실제 모델 대신 가짜 `claude` 실행 파일을 PATH 앞에 두고 16회 구성 전체가 실행·요약·판정까지 도는지 확인했다. 이 글의 결과 숫자는 2026-09-03에 원래 스크립트로 실제 모델을 돌려 얻은 것이고, 이번에 모델을 다시 돌리지는 않았다.

## 확인 범위와 한계

이 실험은 방향을 보여 줄 뿐 효과 크기를 말해 주지 않는다. 조건마다 2회뿐이고, 모델 하나와 CLI 버전 하나, 파일 네 개짜리 합성 프로젝트에서 한 관찰이다. 실제 저장소처럼 큰 맥락과 긴 세션, 여러 규칙이 함께 걸린 환경에서 같은 방향이 나온다는 보장은 없다.

규칙과 과제를 한 쌍씩 묶어서 규칙 효과와 과제 효과가 섞여 있다. C는 fixture 문서가 규칙 내용을 이미 담고 있어 순수한 규칙 효과를 분리하지 못했다. headless 실행이라 질문이 곧 종료였고, 사람이 답하는 환경에서의 비용은 재지 않았다.

본 실행 전에 정한 것은 비교 항목과 무효 판정 기준까지이고, 무효 기준도 첫 시도가 실패한 뒤에 정했다. 기존 실패 보고 여부와 작업 폴더 독립 판정은 결과를 본 뒤인 2026-10-15에 추가했고, 그 과정에서 판정기 오류를 한 번 고쳤다. 비용은 CLI가 보고한 `total_cost_usd`이며 실제 청구액과 다를 수 있다. 실험 이후 기본 모델이 바뀌었으므로, 지금 쓰는 모델에서 같은 결과가 나오는지는 직접 돌려 봐야 안다.

## 결론

이번 16회에서 규칙 한 절이 에이전트의 행동을 바꾼 경우는 둘이었고, 두 경우 모두 방향은 "구현 대신 질문"이었다. 검증을 재촉하거나 보고 형식을 정한 규칙은 결과물을 바꾸지 않았고, 바뀐 것은 재확인 절차와 보고의 모양이었다. 그 보고에는 남은 위험을 꺼낸 경고와 하지 않은 확인을 했다고 적은 문장이 한 번씩 섞여 있었다.

지시문에 규칙을 더하기 전에 두 가지를 확인해 볼 만하다. 규칙 없이 돌려도 그 행동이 이미 나오는지, 그리고 행동 앞에 조건을 거는 규칙이라면 명확한 과제에서도 멈추는지다. 둘 다 같은 과제를 규칙만 바꿔 두 번씩 돌려 보면 확인할 수 있다.
